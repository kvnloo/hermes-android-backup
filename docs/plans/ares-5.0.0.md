# Ares 5.0.0 Implementation Plan

> For Hermes: implement and exercise the workflows, not a gallery of placeholders. Use isolated feature branches and review against the evidence for each workflow.

**Goal:** Make Hermes Desktop’s client-side workflows available in Ares Classic and NextGen, including working Windows notifications. **Excluded:** bundling, installing or operating a local Hermes host or a local inference engine from Ares. A remote gateway may itself use any model; that never makes Ares the host.

**Architecture:** One Flutter client with shared services and accessible actions for both layouts; use native adapters for genuinely platform-specific interactions. Existing gateway-companion APIs and the published Desktop Webapp protocol are legitimate remote resources. An external URL, mock API, instructions to type a command, no-op button, or credential-forwarding WebView is not native workflow parity. Where an upstream feature is Electron-local, implement a user-authorised gateway-side equivalent or explicitly leave it open. No shell or command execution via invented generic endpoints.

**Tech stack:** Flutter/Dart, native runners (Android, iOS/iPadOS, macOS, Windows; Linux runner is in scope), existing Hermes gateway protocols. Existing local Apple/Windows branches and uncommitted signing work stay untouched. Work from the integrated port plus current main, not a stale Android checkout.

## Coverage and acceptance

The companion `ares-5.0.0-scope.md` preserves every row and its detailed acceptance target from the pinned feature audit, including the single excluded row, plus Windows native notifications. Track smaller controls in the linked source appendix rather than treating broad family names as one checkbox. A feature is not done without an entry point from both current navigation trees, capability/scoping/error handling, tests through the real entry point, and evidence for applicable platforms. For unavailable hosts, report what capability is missing and retain an acceptance gap. A blocked card never releases the candidate.

- Cross-platform by default: Android (store and direct build), iPhone/iPad, macOS, Windows and Linux where the feature applies. Reflow panes into sheets/fullscreen views on narrow devices; do not equate mobile with unsupported. For driving surfaces restrict interactive workflows to parked use. Global OS hotkeys, tray, external window capture, OS toast registration and desktop windows may need distinct adapters or documented constraints.
- Windows notifications: real OS toasts, app identity, categories/preferences, dismissal or disabled state, click/open correct connection/session, stale/duplicate handling and separate verified gates for packaged/unpackaged, foreground/background and cold activation. No live secret, transcript or approval action in activation args. Never act on a command solely because a toast payload asked.
- Access/authority: pin workspace operations to connection/profile/session, canonical cwd and declared host capabilities. No token in URLs/logs or arbitrary embedded origins. Confirm irreversible actions; never auto-approve, auto-purchase or elevate. Use throwaway fixtures, not personal live chats, paid accounts or production gateways. No new copyleft core dependency without Sam’s approval. Do not deploy, tag, publish, or submit until explicitly cleared and all gates pass.
- Validate with focused Flutter widget/contract tests first; also run `flutter analyze --fatal-infos`, full applicable suites, store-flavour checks and native build/smoke tests at integration. Windows toast must show up in the actual Windows notification system, not only in a Dart mock. Keep tests, failures and remaining platform gates distinct.

## Delivery graph

1. **Windows notifications**: inspect `lib/core/services/turn_notification_service.dart`, `lib/core/utils/platform_capabilities.dart` and `windows/runner/`; verify the Windows sink with a synthetic, non-sensitive toast and exact activation route. Do not disable the Android/Apple sinks.
2. **Chat discovery and history**: `workspace_sessions_screen.dart`, `sessions_sidebar.dart` and the active chat surfaces. Reuse existing FTS/branch RPCs; build transcript find, prompt jump and reading-position persistence; expand lifecycle, import/export and organisation from the scope file.
3. **Remote ownership and fleet**: define stable per-connection/profile/session request adapters, SSH/Cloud discovery and lifecycle, cross-gateway dispatch, remote Webapp access and auth. Provide contracts for dependent tools; never weaken TLS or infer missing server data.
4. **Queue, worker and composer controls**: use actual owner APIs, retain admission IDs, test reconnect, simultaneous clients, lost outcomes and orphan drafts. Implement child-targeted steering and advanced composer/command actions.
5. **File/terminal/Git workspace**: file tree and conflict-aware editor, per-turn and working-copy review, safe worktree/PR operations, reconnectable real PTYs. Build on the remote-owner contract.
6. **Browser, artifact and plugin surfaces**: integrate isolated previews, session-scoped annotations, transcripts/widgets, rich media, plugin contribution/consent. Keep privilege boundaries between browser content, extensions and the gateway.
7. **Agent management**: profile lifecycle and transfer, capabilities, provider/auth/routing and billing, memory, bot groups, gated Bot Desktop, Kanban, messaging/webhooks, cron and host maintenance. Verify APIs independently; never claim a command-output dump replaces the UI.
8. **System integration, presentation and voice**: common navigation and notification refinements; platform implementations of panes/windows, tray, HUD, power, capture and shortcuts; accessibility/appearance/languages/help, Petdex, Radio, voice engines where supported. Restore Apple parity with main, include Linux runner/testing.
9. **Integration and verification**: rebase/merge only reviewed local feature commits; rebuild/reverify shared dependencies and all OS variants. Validate the individual acceptance clauses and negative cases, not just a green build. Only then prepare release assets for 5.0.0.

**Progress source:** local Hermes Kanban board `ares-v5-0-0`, worktree `feature/ares-v5.0.0`. Cards marked running, partial or blocked are not shipped. Keep build numbers and notes on a development branch; a manifest version is not a release declaration.

**F18 / C06–C07 text increment:** In a blank new Classic or NextGen chat, **Recover a text draft** lists this account’s saved drafts. Selecting a stored session copies its text only after the metadata endpoint explicitly reports that session missing. A still-existing chat, plain 404, failed check, changed account or intervening edit does not authorize a copy. A never-sent NextGen chat has a separate device-local key and needs no server lookup. Undo removes only the untouched copy; the original is retained. Older Classic drafts without account provenance are not offered across chats. Plain Up/Down in an empty focused composer walks the loaded session’s user prompts and returns to the present without sending. This increment does not establish queue, image-outbox or native-platform acceptance.
