# Gateway queue and draft recovery (F18)

**Status: partial.** The stock authority owns the FIFO; Ares does not own its scheduler. In an attached canonical chat, open **Gateway queue** in either toolbar. NextGen's mid-turn **Queue** choice also opens it with the text to review. Submit adds a new admission (it may start immediately when idle). Edit replaces a still-queued text row at the tail. Remove confirms that if the row starts during the operation, the host may interrupt *that row*. Steer is available only on rows advertising it. There is no send-now button for server admissions.

**Paused: unknown outcome** is the authority's state after it loses an execution. **Discard… → Discard and resume** resolves that admission with its own execution generation, not the current turn's. Ares never resubmits the lost prompt. Other clients' pending-change events request a new scoped snapshot; reopening the chat reads the gateway rather than replaying a local outbox. An unsuccessful mutation or read-back is not retried automatically. A queued edit uses a separate editor and cannot overwrite the chat draft.

**Client-held park** follows Desktop 0.23.4. Prompts that have not been admitted stay on this device. Stop or Esc parks that list and shows **N queued — paused** with **Resume**. Resume, or Enter on an empty idle composer, lifts the park and admits the head only when the turn is idle. A row's **Send queued prompt**, or Enter on an empty composer while a turn is running, unparks, moves that row to the head and interrupts; the settle then admits it once. Enter with nothing queued does not stop the turn. Queueing a new prompt also lifts the park. Canonical busy input is still admitted straight into the gateway FIFO, and nothing in this client holds or releases a healthy FIFO. A failed turn parks the same client-held list so it is not sent into the error. That park stays in both layouts.

An automatic drain peeks the next entry and removes it only after the send is accepted. A refused drain leaves that prompt at the head, parks the list, and shows the send error. Resume, or the row's send, is the retry. Classic does not keep a second copy in the composer. NextGen still shows a refused prompt on its bubble with Retry, because that layout removes the row when it hands the prompt to send.

While a row's editor is open, the drainer skips that row. Later rows still drain in their original order. Saving after the row has gone says that the unsent prompt is no longer in the queue.

Classic stores those prompt texts for the same owner and stored session as the draft store. It does not store credentials or attachments. Leaving the chat and opening it again restores the texts parked, and does not send them. Unparking is unconditional: a row send or Resume while Stop is still in flight lifts the park immediately, and the drain runs after Stop clears its in-flight flag. NextGen's client-held list remains in memory for that visit.

## Contract and open requirement

Verified against Hermes [`b7ee21c14e38316273f88d8ed112491ba1c87d15`](https://github.com/NousResearch/hermes-agent/tree/b7ee21c14e38316273f88d8ed112491ba1c87d15):

- `gateway/session_controls.py` and `tui_gateway/contracts/canonical_sessions.py`: `session.resume` on the already attached parent, `omit_messages:true`, returns **top-level `pending`** (Desktop's `info.pending_submissions` is a renderer projection). Check the stored/runtime session, effective profile and immutable FIFO identity. `ref.profile_id` is the owner's opaque identifier, not its display name.
- `persistence/sqlite/authority/_admission_store.py`: `submission_id` identifies the client intent; the server mints a **different** `admission_id`. `prompt.submit` and `prompt.replace_queued` carry a submission identity. `prompt.cancel`, `prompt.steer_queued`, `prompt.replace_queued` and `prompt.resolve_unknown` address the original server admission. After an acknowledged write Ares reads the resulting admission with `prompt.receipt` on the same owner before reporting confirmation.
- `gateway/session_queued_controls.py`: the host fences a row that was claimed while its edit was open. Removing or replacing rows and then copying them back later is **not** pausing: it retires admissions, settles waiters and changes sequence/order. `session.interrupt` does not park the durable FIFO.
- **Scope:** the canonical inventory still has no operator hold of a healthy FIFO, and Ares does not invent one. Desktop's `$parkedQueueSessions` is the contract that was adopted: it gates only the client-side drainer (`shouldAutoDrain` skips a parked session; drain submits entries with no `serverStatus`). `prompt.resolve_unknown` remains the only way to release a FIFO paused on an unknown head.

## Recovery coverage

- **Text:** in a fresh Classic/NextGen composer, copy a lost draft only from this account, after explicit session-not-found evidence (or a never-sent device-local draft). Undo removes only the unchanged copy. A failed lookup or intervening edit, including typing and clearing, does not authorise restoration. Up/Down in the focused empty editor recalls loaded prompts without submitting.
- **Stock image sends:** private app storage holds the original caption and image bytes before upload. An interrupted upload restores as a copy. After upload, frozen refs, ordered images and request identity are recorded before prompt dispatch. Recovery fills an unchanged empty composer only by explicit gesture. Unchanged identified requests can reuse their frozen identity on explicit Send; changed inputs and mutable/identityless legacy uploads are new intents. A matching canonical RPC response names the session in `ref` and does not echo the client's UUID. Sensitive image/text journals are local application data, not part of the metadata-only recovery-v2 WAL.
- **Limits:** ordinary image-only/image-plus-text stock sends. Mixed files and slash commands do not gain frozen-image replay. Classic REST/SSE and companion recovery-v2 do not either: on an empty composer those transports show a capability explanation instead of **Recover image draft…**, and they do not borrow a stock receipt. See [live workers](remote-workspace-workers.md) for F20.

## Verification

`gateway_queue_wire_test.dart` uses two real Ares client adapters with a disposable WebSocket/HTTP peer and a shared fixture ledger. It covers cross-client changes, explicit discard on a fresh socket, stale rows/route invalidation and lost acknowledgement with no second submit. `workspace_workers_navigation_test.dart` drives both actual chat entries, edits an admission, confirms discard, receives a remote change and revokes the account. `client_held_rest_refusal_test.dart`, `client_held_recovery_resume_test.dart` and `client_held_edit_race_test.dart` cover a refused drain, Resume and row send during Stop, an edit that must not drain, and a Classic queue restored parked. `client_held_queue_toolbar_test.dart` drives both real composers: Stop parks, Resume and empty Enter drain, and a busy row or empty Enter admits the chosen prompt once. Esc uses that same stop. Classic REST/SSE and companion recovery show the capability explanation instead of **Recover image draft…**. `prepared_image_*`, `composer_orphan_recall_test.dart` and `nextgen_test.dart` cover restoration and local drain races. These are not packaged OS/device tests.

The pinned upstream `tests/gateway/test_prompt_queued_controls.py` and `test_authority_unknown_resolution.py` (excluding the provider-conversation case) independently exercised the actual SQLite store, a restarted owner, exact-once settlement and refusal paths using disposable directories and fixture executors. `tests/tui_gateway/test_subagent_roster.py` exercised the real roster handler. No deployed gateway or provider was used. The full two-file attempt timed out in the extra loopback-provider scenario; it is not counted as a pass. The focused client run and independent handler run are separate evidence, not an end-to-end deployment.
