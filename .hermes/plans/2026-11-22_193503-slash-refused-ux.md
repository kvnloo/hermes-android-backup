# Ares slash-refused UX fix — implementation plan

> **Historical contributor plan, superseded by maintenance review.** See
> `docs/SLASH_COMMAND_UNSUPPORTED_AUDIT.md` for the implemented contract.
> In particular: refusals retain drafts even without a catalog; no RPC failure
> automatically resends prose; 4018 alone is not a refusal verdict; learned
> memory is connection-owned (not mutable catalog state); local arguments are
> not silently ignored and browser navigation is explicitly route-qualified.
> The original audit totals are unreconciled. Full-suite/manual-device and
> independent-review claims below are proposed gates, not current acceptance.
> Current maintenance runs focused affected tests only; fresh independent
> review and exact-head CI remain required before ready/merge.

**Goal:** Stop the 51 gateway-refused slash commands from leaking into Ares chats as plain-text prose, surface the gateway's refusal hints, wire the commands that already have app equivalents, and shrink the dropdown to commands that can actually run.

**Architecture:** Three client-side changes on the existing slash pipeline (`SlashCommandController` → `slash.exec` → `chat_screen._dispatchSlashCommand`), plus one upstream ask tracked on PR #302. No hardcoded command mirrors — the client learns refusals from the server's own `unsupported_command` answers, and the end-state is the gateway publishing an `executable` set the app's parser already tolerates.

**Tech stack:** Flutter/Dart, existing widget/unit test suite (`flutter test`), stock Hermes gateway RPCs only (`commands.catalog`, `slash.exec`, `session.steer`, `session.branch`).

---

## Current context / assumptions

- Audit (PR #302, `docs/SLASH_COMMAND_UNSUPPORTED_AUDIT.md`): 45 of 98 stock commands execute; 52 refused with `unsupported_command`; `/new`+`/reset` already intercepted locally (#301).
- Today a refusal hits `_isSlashUnsupported(error)` in `chat_screen.dart` (~line 4627) and `return null` → the text falls through to the ordinary prompt send. The test `test/slash_command_controller_test.dart:942` ("an unsupported command falls back to the plain send") pins this behavior — it must be inverted, not deleted.
- `JsonRpcError.fromGateway` (`ws_client.dart:67`) already carries `data`, so the gateway's `REFUSAL_HINTS` (`data.detail`, e.g. "Run `hermes profile export …` in a terminal") reaches the client and is currently discarded.
- The catalog's `desktop` metadata (`terminal`/`hidden`/`advanced`) is display intent, NOT the refusal set (audit: `/cron` is `terminal` but works; most refused rows have `desktop: null`) — do not filter on it.
- `SlashCommandCatalog.fromResult` already honors an `executable`/`supported`/`slash_exec` key if the server ever sends one (`slash_command.dart:_advertisedExecutable`).
- The catalog cache is invalidated on connection/scope change (`controller.invalidate()`), so learned refusals naturally reset per connection.
- Lesson from #301: intercepts must canonicalize the name first (`slashCommandName` handles `//new`, case) — reuse it, never a raw string set.

## Proposed approach (three client fixes + one upstream ask)

1. **No prose leak.** A refused command that IS in the loaded catalog gets a local notice card (the existing `SlashCommandNotice` surface used by `/status` output) showing the gateway's `data.detail` hint when present, else "This command isn't available on this server." The plain-send fallback survives ONLY for `/`-lines whose name is not in the catalog (genuine prose starting with a slash).
2. **Learned refusals.** When `slash.exec` answers `unsupported_command` for a catalogued name, mark it in a mutable `refused` set on the loaded `SlashCommandCatalog`. The dropdown filters refused names out for the life of the connection. No static mirror list; self-corrects if a server update starts accepting a command (next connection).
3. **Wire the equivalents.** Local intercepts (same pattern as `/new`): `/model` opens the existing model picker, `/sessions` and `/resume` open the session browser. `/steer` and `/branch` stay on the notice path (they are mid-turn actions Ares already exposes via UI; wiring slash text to them is deferred — YAGNI until asked).
4. **Upstream ask (tracked, not blocking):** request on #302 that stock `commands.catalog` publish an `executable` set (or stop advertising refused rows for non-terminal surfaces). When it lands, delete the learned-refusal set and gate the dropdown on `catalog.canExecute` — the parser already supports it.

## Risks / trade-offs / open questions

- **First-use penalty:** a refused command shows its notice on first use before the dropdown hides it — accepted (a learned filter needs one observation; the alternative is a hardcoded mirror list, which #301 proved drifts).
- **Prose fallback narrowing:** users who intentionally send `/something` as literal text to the agent keep working only when the name is not catalogued; catalogued-name prose is now blocked — flag in PR body for maintainer visibility.
- **`/steer`/`/branch` slash wiring deferred** — their app equivalents are gesture/UI-driven mid-turn; revisit if users ask.
- **Open:** does upstream prefer filtering in the app, in the gateway catalog, or both? Task 4 asks; Tasks 1–3 land regardless.
